# Ref writers

**Status:** proposed.

## Problem

The server stores refs but does not control who writes them. Every worker
container is on `caos-net` and can reach the server's smart-HTTP
`receive-pack`, so any job, including a shell running model-written commands,
can push any ref. `client-owned-conversation-refs.md` accepted this on purpose
("a buggy or malicious worker with repository access can rewrite conversation
refs"). This doc reverses that decision for refs in general. Conversations are
the first user, and are covered by a short extension at the end.

## Goals

1. **Several writers per ref.** More than one person, and each person's jobs,
   can write the same ref. Multiplayer conversations are the motivating case.
2. **Writers can be removed**, and removal takes effect at the next push. It
   does not wait for credentials to expire.
3. **Anyone can read.** Reads are not restricted.
4. **A job that can write can pass that right to the runs it creates**:
   continuations, map children, and subagents. It can pass only what it holds.
5. **It works from Claude cloud sessions.** A cloud container starts fresh
   every session, and its environment is fixed when the session starts. So
   nothing can be required per ref or per conversation on the client side.

## Non-goals

- **Read confidentiality.** Objects live in one shared, content-addressed store
  (`uploadpack.allowAnySHA1InWant`), so anyone holding a hash can read the
  object. Confidentiality would need encryption or a separate server.
- **Protection from the server.** The server holds every secret and runs every
  job. It is trusted, and this design does not change that.
- **Different permissions for different paths within one ref.**

## Keys

Each person has one **writer key**, an ed25519 keypair.

- **The private key stays with the client and never reaches the server.**
  - On a laptop it is a file.
  - In a cloud session it is the `CAOS_WRITER_KEY` variable in the
    environment's settings. It is set once, read by every session, and
    unchanged when conversations are created or shared.
  - It is generated by `caos-cli writer-key new` on a machine the person
    controls. That command prints the private key to a file and the public key
    to stdout.
- **The public key is not secret.** You hand it to whoever should add you as a
  writer, over any channel.
- **Several devices** can share one key, or each have its own. A writers list is
  only a set of public keys, so a person with two keys lists both.

This key is separate from the SecretWriterKey (SPEC, "Secrets"). That key can
replace every secret a person has. This one can only write refs where the
person is listed.

## Governed refs

### Namespaces

Governed refs live in **namespaces**:

```text
refs/caos/w/<id>/writers      the namespace's authority
refs/caos/w/<id>/<anything>   governed refs: any name, any object type
```

- **`writers` is a commit chain.** Each commit's tree holds one file,
  `.caos/writers`:

  ```text
  # <ed25519 public key, 64 lowercase hex>  <label: display only, never checked>
  3b6a27bcceb6a42d62a3a8d02a6f0d73653215771de243a63ac048a18b59da29  malcolm
  9d61b19deffd5a60ba844af492ec2cc44449c5697b326919703bac031cae7f60  nishu
  ```

- **`<id>` is the oid of the root commit of the `writers` chain.** The name is
  the hash of content that includes the first writers list, so no one can
  claim a namespace before its creator does.
- **One `writers` ref governs every ref in its namespace.** A conversation's
  head, its subagents' heads and anything else in the namespace answer to one
  list, so removing a writer covers all of them at once.

The writers list lives in its own ref rather than inside each governed ref's
content. A governed ref can point at anything: a source-tree branch, a bare
tree, a conversation. None of them should have to carry a `.caos/writers`
file. A separate ref also means a change to the writers never races with
appends to a conversation head, because each has its own compare-and-swap.

### Creating a namespace

The creator builds a root commit whose `.caos/writers` lists at least
themselves. They then push it to `refs/caos/w/<that commit's oid>/writers`,
signed with their key (see "Proving a write"). Other refs in the namespace
cannot exist until `writers` does.

### Changing writers

A change to the writers is a new commit on the `writers` chain. The hook
accepts it only if all of the following hold:

- it is signed by a key listed in the **current** `writers` commit (`old`), so
  nobody can add themselves;
- `new` descends from `old` (fast-forward only), so the history of who added
  whom is kept;
- `new`'s `.caos/writers` parses.

**Only a writer key can change the writers, not a run token** (see below). Jobs
write content; a person decides who else may write. A prompt-injected job then
cannot add an attacker. In a cloud session the agent still changes writers
through `caos mcp`, which holds the person's key. That is the person acting,
not a job.

Every writer has equal power, including over the list. Owner roles can be added
later if needed. An empty list freezes the namespace, which is how to archive
it.

### Removing a writer

Removal is a commit that drops the key, and it takes effect on the next push.
It also revokes that person's running jobs, because a run token resolves to its
writer's key at push time (below). A removed writer keeps everything they have
already fetched, and can fork it into a namespace of their own.

## Proving a write

Every push to a governed ref carries one `caos-auth` push option
(`git push -o caos-auth=…`). The option takes one of two forms, depending on
who is pushing.

### A client signs

```text
caos-auth=sig:<pubkey>:<expiry>:<signature>
```

The signature covers:

```text
caos-ref-update v1
<expiry, unix seconds>
<old> <new> <ref>      one line per command, sorted by ref
```

- **Signing the move rather than the commits.** A signed commit says who wrote
  some content. It does not stop anyone from moving a ref back to an older
  signed commit, or to a different commit signed by the same key. What needs
  authorizing is the move: `(ref, old, new)`. Commit hashes are content here,
  and they stay untouched.
- **`old` makes replay mostly useless.** Clients already push with
  `--force-with-lease`, so a captured signature applies only while the ref is
  at `old` again. That can happen only if a writer moves it back there. The
  expiry, a few minutes out, closes that remaining window.
- **`--atomic` multi-ref pushes are signed as one set.**

### A job presents a run token

```text
caos-auth=run:<token>
```

A job never holds a writer key. When the server dispatches a job that has
write authority (next section), it creates a random token and records
`token → (writer pubkey, namespaces, run)`. It injects the token into the job
at `/secret/caos-write`, using the same mechanism and log scrubbing as
secrets. The token dies when the run ends.

The hook resolves the token to its writer key and checks that key the same way
it checks a signature. That is why removing a person revokes their running
jobs: the token resolves to their key, and the key is no longer listed.

## Who gets a run token

Write authority follows one rule: **writes are requested in content and
authorized out of band.**

- **Request.** A job asks to write by carrying a `writes` arg in its ArgTree: a
  space-separated list of namespace ids. It is content, so it shows up in
  traces and is part of the cache key. A job without `writes` never gets a
  token. A shell tool, for example, never asks.
- **Authority.** Authority comes from outside the ArgTree, the way
  SecretReaderKeys do:
  - **A top-level request** carries a header signed by the client's writer key:

    ```text
    X-Caos-Write: <pubkey> <expiry> <namespace,…> <signature over sha256(request body), expiry and namespaces>
    ```

    The signature binds the authority to that one request body, so a leaked
    header cannot be attached to other work.
  - **Every other run** gets its authority from the run that created it.
- **Grant.** A job's token covers `writes ∩ available`.
  - `available` is the header's namespaces for a top-level request.
  - For a continuation or a child (`run-then`, `map-then`, detached requests),
    it is **the namespaces its creator actually received**.

The server already threads `secrets::Context` from a run to its sub-runs. The
write authority goes alongside it.

Goal 4 falls out of the intersection. A job delegates by putting `writes` in a
child's args, and it can only pass on namespaces it holds. Suppose `llm-step`
holds a conversation's namespace:

- it hands that namespace to `run-and-update-ref` and to child `llm-step`s;
- a shell it starts gets no `writes`, so nothing that shell starts can get any
  authority either.

Caching works as it does today:

- **A cache hit runs nothing**, so it writes nothing and gets no token.
- **An unauthorized request for an ArgTree that is not cached** runs without a
  token. Its push is refused and the job fails, so the failure is not cached as
  a result.
- **Two requesters sharing one in-flight run** share the authority of the
  request that started it.

## The hook

A pre-receive hook in the server's repository checks every push. Because it is
a repository hook, it covers smart HTTP and the iroh transport, which spawns
`receive-pack` directly. The server's own writes (`refs/caos/res/*`,
`refs/caos/locator-trees/*`, import markers) do not go through
`receive-pack`, so the hook never sees them.

| Ref | Accepted when |
| --- | --- |
| A content-named ref: `refs/caos/req/<h>`, `refs/heads/caos-test/<h>` | it points at `<h>` |
| `refs/caos/w/<id>/writers`, creating it | `new == <id>`, `new` is a root commit, and the signer is in `new`'s list |
| `refs/caos/w/<id>/writers`, updating it | the signature is from a key in `old`'s list, and `new` is a fast-forward of `old` |
| `refs/caos/w/<id>/<other>` | the signer's or token's key is in the current `writers` list; a token must also include `<id>` in its namespaces |
| anything else | rejected |

- **The cost is one blob read per namespace touched.** No history walk.
- **A push either passes as a whole or is rejected as a whole**, which keeps
  `--atomic` meaningful.
- The hook needs `receive.advertisePushOptions=true` in the repository config.

## Claude cloud sessions

- **Environment setup, once:** add `CAOS_WRITER_KEY` to the environment's
  settings, next to the SecretReaderKeys.
  - Bootstrap reads it from the environment. It never appears in the setup
    script's text, the way `--secret-readers` does today. That flag should move
    to an environment variable for the same reason.
- **In a session:**
  - `caos mcp` signs its own pushes (conversation commits, `writers` changes)
    with the key.
  - It sends `X-Caos-Write` on the requests it submits.
  - Every job those requests start, and everything those jobs delegate to, gets
    its authority from that header (goal 5).
  - The container keeps nothing between sessions, and nothing is needed per ref
    or per conversation.

## Extension: conversations

- **A conversation is a namespace.** `refs/caos/v3/conversations/<hex id>/head`
  becomes:

  ```text
  refs/caos/w/<id>/head
  refs/caos/w/<id>/children/<child>/head    subagents
  ```

  The conversation's id is its namespace id. The session-derived name in use
  today (`cc/<session>`) moves into `.caos/` metadata.
- **Multiplayer:**
  1. Nishu sends Malcolm their public key.
  2. Malcolm adds it to the conversation's writers: from the TUI, or through a
     `caos mcp` tool in his cloud session.
  3. Nishu resumes the conversation by id from their own TUI or cloud session.
     `mcp/resume.rs` already resumes by hash.
  4. Each person's pushes and jobs carry their own key, so the conversation
     log shows who drove each turn.
- **Subagents share the parent's namespace.**
  - `llm-step` lists the namespace in a child's `writes`.
  - Removing a writer from the conversation also removes them from every
    subagent.
  - No key is created at runtime.
- **Per-user refs** (`refs/caos/v3/users/<user>/conversations/{active,archived}/…`,
  the sidebar) move to a **personal namespace**.
  - Its root commit is fixed: the tree holds `.caos/writers` with one key, the
    commit has no parent, and author and committer are both `caos <caos>` at
    time 0.
  - Anyone can compute a person's personal namespace id from their public key,
    so nothing needs looking up, and only that key can write there.

## Migration

| Pushed today | Becomes |
| --- | --- |
| `refs/caos/req/<h>` (`ensure_pushed`) | unchanged; content-named |
| `refs/heads/caos-test/<sha>` (`std/caos-test`) | unchanged; content-named |
| `refs/caos/v3/conversations/…`, `refs/caos/v3/users/…` | namespaces, per the extension above |
| `refs/caos/dev` (`caosd up --iroh`) | open question below |
| test fixtures pushing `refs/heads/*` to scratch servers | a test helper that creates a namespace with a throwaway key |

Roll out in two steps:

1. **Report-only.** The hook logs what it would reject and accepts everything.
   One suite run then lists every writer that the table above missed.
2. **Enforce.**

## Alternatives considered

- **Sign commits instead of ref moves.** This doesn't stop rollback, and it
  changes commit hashes. See "Proving a write".
- **A keypair per ref, shared as an invite.** Holding the private key would be
  the right to write. It has three problems:
  - removing someone means moving everyone to a new ref;
  - everyone signs as the same key, so you can't tell who wrote what;
  - a cloud session can't hold a key per conversation.
- **Put the writer's private key in the secret store for jobs to sign with.**
  This works, but it hands every person's private key to the server, and it
  grants by image, so it can't express "this job may pass it on". Run tokens
  keep keys on clients, and the `writes` intersection scopes delegation.
- **`.caos/writers` inside each governed ref's own content.** This doesn't work
  for refs that aren't conversations; see "Namespaces".

## Open questions

- **`refs/caos/dev`.** An operator pushes it, and cloud bootstrap reads it by
  name. Two options:
  - an operator namespace, with bootstrap given its id;
  - a server-config allow-list of unguarded refs.

  The allow-list is simpler. Every entry in it is a ref any job can rewrite.
- **Token lifetime for detached children.** A detached child can outlive the run
  that started it. Its token should probably die with its own run rather than
  its creator's. The creator's authority was checked when the child was
  created, and removing a writer revokes the token anyway.
- **Server identity in the signed text.** A signature is replayable on another
  server holding the same namespace until it expires. Adding the server's
  identity closes that, if the window matters.
